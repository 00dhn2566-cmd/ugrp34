## 왜 이 일이 남았나 — 배분기로는 못 잡는 게 있다

스펙 배율 `s` 를 깎는 것은 **궤적**을 늦출 뿐 **루프**를 못 바꾼다. 그래서 한계사이클,
외란 복귀, 지연이 만든 불안정에는 손이 안 닿는다 (§8g 표 넷). 남는 레버는

  ① 지연 줄이기  ② 루프 재튜닝  ③ **지연 보상**  ④ 운용 조건으로 적기

이고, 이 문서는 ③ 이다.

## 이미 해 본 것과 그 결과 (반복하지 말 것)

**리드 보상기 = 실패.** `Scripts_Data/qc_predictor_apply.m`, 폐루프 실측.
지연 블록 뒤에 `(1 + 0.7τ·s)/(τ_f·s + 1)`, 고주파 이득 3. 계산상 11.08 Hz 에서
위상 **+26~27°** 를 주므로 한계사이클을 죽여야 하는데, 실제로는

| | 추종 | 밀림 | 복귀 | roll 진동 |
|---|---|---|---|---|
| 20 ms 무보상 | 7.66 cm | 4.54 cm | 1.72 s | 1.156° @ 11.08 Hz |
| 20 ms 리드 | 7.27 cm | 5.50 cm | 1.91 s | **3.693° @ 3.90 Hz** |
| 60 ms 무보상 | 14.39 cm | 8.04 cm | 6.17 s | 10.49° @ 5.54 Hz |
| 60 ms 리드 | 12.57 cm | **23.48 cm** | **10.99 s** | 12.53° @ 6.29 Hz |

**없앤 게 아니라 더 크고 느린 한계사이클로 갈아치웠다.** 고도까지 무너졌다
(60 ms 리드, t>3 s 의 z 낙차 23.6 cm). 추종만 개선되는 것이 핵심 단서다.

**왜 실패했나.** 리드는 늦게 온 신호를 **늦게 온 기울기로** 민다. 11 Hz 면 반주기가
45 ms 라 20 ms 전 기울기도 이미 위상이 어긋나 있다. "위상 +26°" 라는 계산은 기울기가
정확할 때만 성립하고, 실제로는 틀린 기울기를 증폭했다. 정상 뒤처짐(저주파)에는
듣고 과도에는 독이다.

→ **기울기는 측정 자신의 미분이 아니라 다른 데서 와야 한다.** 자세/IMU 경로는
경로 지연이 5 ms 라 사실상 현재 값이다 (§8c T2).

## 다음 판: 지연 구간 MHE (사용자 설계 2026-08-28)

> "지연시간 동안만 MPC 돌려서 센서값 보정하고, 나머지 계산은 그거 기반으로 해서
>  나머지 동안은 출력이 지나갈 거다 해서 중요 지표 기반으로 넣는 게 좋을 듯."

이름은 **MHE(moving-horizon estimation)** 다. MPC 의 추정 쌍둥이 — MPC 가 **미래**
구간에 대해 입력을 최적화한다면 MHE 는 **과거 지연 구간**에 대해 상태를 최적화한다.
여기서 필요한 건 후자다 (미래 경로는 이미 상위 계획기가 준다).

### 구조 — 두 속도, 그리고 **사이 구간에도 센서를 읽는다**

사용자 설계 (2026-08-28, 정련판):
> "지연 시간 기반해서 보상기 계산 비율을 결정하고, 가끔은 제대로 MHE 돌리고,
>  다른 경우는 가장 최신 MHE 사용해서 **중요 지표 몇 가지만** 사용해서 센서값 보정."

```
N 스텝마다 (느린 쪽)   구간 [t-τ, t] 에 대해 풀기:
                         min ‖측정 잔차‖² + ‖모델 잔차‖²  over (상태, 바이어스)
                       입력은 그 구간에 **실제로 넣은 제어 명령** (지연 없이 안다)
                       산출 = 축당 **세 숫자**: (Δ0, Δ0_dot, b)
                         Δ0     보정 오프셋 (그 시점의 p_hat - p_sensor)
                         Δ0_dot 그 변화율
                         b      추정된 가속도 바이어스

매 스텝 (빠른 쪽)      p_hat = p_sensor(지연된 그대로) + Δ(δ)
                       Δ(δ)  = Δ0 + Δ0_dot·δ + ½·b·δ²      (δ = 마지막 해 이후 경과)
                       곱셈 두어 번.
```

★ **핵심은 사이 구간에도 센서를 매 스텝 읽는다는 것이다.** 지금 구현
(`AxisPredictor.step`)은 사이 구간에 **자기 상태를 적분**한다 — 그동안 센서가 루프에서
빠져 있어, VIO 가 튀어도 출력은 모른다. 위 구조는 출력이 언제나 "센서 + 보정" 이라
센서가 튀면 출력도 같이 튄다. **사용자가 08-28 에 제기한 "센서값이 틀렸다 간주하는
것이라 조심해야 한다" 는 우려를 구조적으로 해소하는 형태다.** 다시 짤 때 이 형태로 갈 것.

세 가지가 따라온다:

1. **추측항법 구간이 없다.** 센서가 매 스텝 닻 노릇을 한다.
2. **실패 모드가 깨끗하다.** MHE 가 낡거나 이상하면 **Δ → 0** 이면 끝이다. 그러면 출력이
   정확히 무보상 = 원 센서값이고, 그건 오늘 전부 측정해 둔 알려진 거동이다.
   (지금 구조는 "적분을 멈추고 어디로 갈지" 를 따로 정해야 했다 — `_snap` 참조.)
3. **감시가 싸다.** Δ 하나만 보면 된다. 물리 상한(`v_max·τ`)으로 자르고, 한계에 닿으면
   `healthy` 를 내린다. 상태 벡터 전체를 감시할 필요가 없다.

### 지금 구현(되감기-재적분) 대비 무엇이 나아지나

지금 `AxisPredictor.correct` 는 "저장해 둔 가속도가 맞다" 고 가정하고 그대로 재생한다.
MHE 는 그 구간에서 **모르는 가속도 바이어스까지 같이 추정한다** — 바람, 질량 오차,
항력처럼 모델이 틀린 몫이 바이어스로 잡힌다. 그리고 **그 바이어스가 다음 N 스텝 동안의
싼 외삽을 정확하게 만든다.** 사용자 말의 "나머지 동안은 그거 기반으로 출력이 지나갈
거다" 가 이 바이어스다. 고정 이득 알파-베타로는 이걸 못 한다.

### N 은 지연에서 자동 — ★ 이 절은 2026-08-29 에 반증됐다 (아래 정정 참조)

되감기/최적화 비용은 τ/dt 스텝에 비례한다. N 스텝마다 돌리면 스텝당 평균은 (τ/dt)/N
이므로 이걸 예산으로 고정한다: `N = ceil((τ/dt) / replay_budget)`.
5 ms → N=1(1 kHz) / 60 ms → N=10(100 Hz) / 100 ms → N=17. **부하가 지연과 무관하게
일정하다.** `PredictorConfig.every_n_for()` 가 이미 이렇게 한다.

★ 사이 구간을 ZOH 로 붙잡으면 최대 N·dt 의 **새 지연**이 생겨 자기모순이다. 반드시
외삽할 것 (곱셈 한 번).

### ★ 정정 (2026-08-29) — 위 규칙은 방향이 반대다. 구현은 `mhe_estimator.py` 를 볼 것

사용자 지적: "지연 시간 커질수록 정교한 예측이 필요해서 N 이 작아져야 하는 것 아니냐."
맞다. 위 규칙은 **계산량 논리로만** 유도됐고 정확도를 안 봤다. 지연이 커지면 오차가
두 번 늘어난다 — 되감을 구간이 길어지고, N 이 커져 바이어스가 더 낡은 채로 더 오래
외삽한다. 게다가 지연의 대가는 선형이 아니라 **절벽**이다:

| tau | 옛 규칙의 N | 그 지연에서 예측기의 값어치 |
|---|---|---|
| 5 ms | **1** (가장 자주) | 배율 1.00 — 고칠 게 거의 없다 |
| 60 ms | 10 | 돌풍 배율 0.28, yaw 표류 23.8도 = 창 통과 실패 |
| 100 ms | **17** (가장 드물게) | 운용 불가 구간 |

**계산을 제일 많이 쓰는 데가 제일 안 중요한 곳이고, 제일 아끼는 데가 생사가 갈리는 곳이다.**

비용 모델이 틀렸던 것도 있다. `tau/dt` 는 **되감기-재적분(naive replay)** 의 비용이고,
MHE 는 창을 한 칸 밀고 직전 해로 **웜스타트**하므로 한 번 푸는 비용이 tau 에 비례하지
않는다. 게다가 이 문제는 선형이라 3x3 정규방정식 한 번이면 끝난다 — 애초에 비싸지 않다.

새 규칙(구현됨)은 **정확도 예산**이다:

    N*dt <= sqrt(2 * accuracy_tol_m / db)      db = 바이어스 불확실도

그리고 **db 는 최소제곱이 스스로 낸다**(정규방정식 역행렬 대각). 추정기가 "내 바이어스를
얼마나 믿을 수 있나" 를 재서 자기 실행 주기를 정한다. 계산량은 그 다음이고 — 목적이
아니라 제약 — 못 감당하면 `n_reason = 'compute'` 로 보고한다. 조용히 나빠지는 것보다 낫다.

곁들여: **tau <~ 30 ms 면 예측기를 꺼도 된다.** 배율 1.00 구간이라 보상할 게 없고
센서를 틀렸다고 가정하는 위험만 진다.

### ★ 새로 나온 제약 — 창 길이는 지연이 아니라 **관측 가능성**이 정한다

설계행렬의 바이어스 열이 `0.5*D^2` 이라, 창이 짧으면 바이어스가 만드는 위치 변화가
측정 잡음에 묻혀 **안 보인다**. 조건은

    0.5 * b * H^2  >~  sigma      ->      H >~ sqrt(2*sigma/b)

b = 0.8 m/s^2, sigma = 1 cm 면 H >~ 0.158 s. 실측(합성):
H=0.06 에서 추정 0.000 / H=0.12 에서 0.525 / **H=0.20 에서 0.954** / H=0.50 에서 0.903.
db 도 2.000 -> 0.378 로 같이 준다 (추정기가 스스로 안다).

**지연은 되감을 거리만 정한다. 창 길이는 그것과 별개로 관측 가능성이 정한다.**
실제 창은 `max(지연, 관측가능성 하한)` 이어야 한다. 이건 물리이지 구현 결함이 아니다.

크기는 g=9.81 의 1.3~1.4 배로 나오는데 유한차분 평활과 루프 상관이 섞인 값이라
**근사로 볼 것**. 기존 `delay_compensator.lateral_accel_from_attitude` 가 yaw=0 에서
`ax = +g*pitch, ay = -g*roll` 을 주므로 **그 함수의 부호 규약이 맞다** (그 함수 주석의
"부호는 반드시 골든 트레이스로 확인하고 쓸 것" 경고가 이로써 해소된다).

남은 확인 1건: **OpenVINS 가 이미 IMU 전파해 내보내는가** (태민). 이미 하면 이중 보상이다.

### Simulink 구현 메모 — 어려운 곳은 수학이 아니다

**수학은 닫힌 해다.** 축당 미지수 셋(p, v, b)에 창 안에서 선형이므로 **3x3 가중
최소제곱 한 번**이면 된다. 반복자도 solver 도 필요 없다. tau=60 ms / VIO 30 Hz 면
창 안 측정이 2개뿐이라 미지수보다 적은데, 직전 추정을 사전분포로 넣어 채운다
(MHE 의 arrival cost).

**진짜 일거리 셋:**

1. **알고리즘을 담을 그릇 — Level-2 MATLAB S-Function 을 쓸 것.**
   MATLAB Function 블록은 본문을 스크립트로 주입하기 까다롭다(Stateflow API 경유).
   Level-2 S-Function 은 알고리즘이 평범한 `.m` 파일로 남아 버전 관리·단위 시험이
   되고, 블록은 `FunctionName` 으로 참조만 하므로 삽입이 한 줄이다 —
   `qc_delay_apply` / `qc_predictor_apply` 와 같은 메모리 수술 방식 그대로.
2. **대수 루프.** 보상기가 제어 명령 u 를 쓰는데 u 는 보상된 위치에서 나온다.
   S-function 의 **direct feedthrough 를 꺼 두면** 풀린다. 놓치면 컴파일에서
   대수 루프로 걸리고 원인 찾기가 성가시다.
3. **벡터 폭 3.** 위치 경로는 3원소다. 오늘 `Transfer Fcn` 이 이것 때문에 죽었다
   (SISO 블록). S-function 은 포트 폭을 선언할 수 있어 오히려 이쪽이 깔끔하다.

**★ 순서: MATLAB 전에 오프라인으로 검증할 것.**
`diagnose/results/worstcase/ts_*.csv` 에 500 Hz 로 x/y/z/roll/pitch/yaw 가 있다.
거기서 **자세를 입력으로, 지연시킨 위치를 측정으로** 먹이고 MHE 출력이 기록된 진짜
위치를 따라가는지 파이썬에서 본다. 부호 오류·이득·바이어스 추정 여부가 **MATLAB 없이**
다 걸러진다. 이걸 통과한 뒤 심으면 왕복이 한두 번으로 끝난다.
오늘 벡터 폭 하나로 사이클 하나(≈4분)를 날렸다 — MATLAB 왕복이 이 작업의 실제 비용이다.

### 반드시 유지할 안전 규약 (이미 파이썬에 있음)

센서가 닻이고 모델은 사이를 메우는 도구다. 둘이 물리적으로 말이 안 되게 어긋나면
**언제나 센서가 이긴다.**

- `age_trust = 0.7` — 보고된 나이의 70% 만 되감는다. 비대칭이 근거다: 과소보상의
  손해는 **성능**(이미 아는 값)이지만 과대보상은 추정을 실제보다 앞에 놓아
  **불안정**이 된다. 1.0 초과 금지.
- 드롭아웃 시한 0.25 s — 측정이 끊기면 추측항법을 멈춘다.
- 혁신 게이트 0.5 m / 이탈 한계 `v_max·age_eff + 여유`.
- `healthy` / `fault` — 말없이 이상해지지 않게. 감독자가 끄고 원 측정으로 되돌린다.

## 시작 전에 확인할 것 두 가지

1. **OpenVINS 가 이미 IMU 전파해서 내보내는가** (태민). 그렇다면 여기서 또 하는 건
   **이중 보상**이다. `/ov_msckf/poseimu` 라는 토픽 이름이 전파를 시사하지만 확인 필요.
   이게 "예" 면 이 작업 전체의 전제가 바뀐다 — 먼저 물어볼 것.
2. **부호.** 이 저장소는 자세 PID 게인이 음수인 것처럼 부호 규약이 직관과 다른 자리가
   있다. 한 번 틀리면 보상이 진동을 **키운다** (리드가 그랬다).
   - 실측 완료: **`a_x = +9.63 · pitch`** (0.98 g, 상관 +0.93, `ts_K.csv` 이동 구간)
   - **미측: `a_y ↔ roll`.** 이 로그로는 안 나온다 (기울기 ~0, 상관 -0.003) — y 가 거의
     안 움직이는데 roll 은 11 Hz 로 떨어서 이중미분이 잡음에 묻힌다.
     **y 방향 이동 미션으로 따로 잴 것.** 추측으로 넣지 말 것.
