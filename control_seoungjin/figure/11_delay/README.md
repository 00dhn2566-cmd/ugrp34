## 이 그림들이 말하는 것

1. **"스펙을 낮춰 버틴다"가 안 먹히는 축이 하나 있다.** 자세 경로 지연은 정지 상태에서
   이미 불안정을 만든다 — 궤적을 느리게 해도 안 고쳐진다. 그래서 여기는 감쇄가 아니라
   **게이트**이고, 넘으면 `mission_allowed: false` 로 임무를 거부한다.
   상위가 이걸 모르면 "느리게 가면 되겠지" 하고 임무를 밀어넣게 된다.

2. **위치 경로는 감쇄가 정확히 먹힌다.** τ=40 ms 에서 전속(v 1.6)은 복귀 12.9 s 로 사실상
   실패인데, s=0.55(v 0.88)로 깎으면 **종단오차 0.00 cm / 복귀 1.14 s** — 무지연 기준
   (1.73 s)보다도 낫다. 사용자 요구가 실측으로 성립한 지점이다.

3. **판정 기준을 조여야 보인다.** "복귀가 존재하는가"만 보면 τ=80 ms / s=0.55 가
   종단오차 4 cm 로 통과한다 — 복귀에 14 s 가 걸리는데도. 목표엔 도착하지만 진동이
   안 잦아드는 상태다. 강건성이 목적이면 복귀 시간이 게이트에 있어야 한다.

4. **감쇄는 선행이어야 한다.** 다리 분석에서, 감쇄를 결정한 뒤에도 새 한계 안으로
   들어가는 데 0.7~3.9 s 가 걸린다 (재계획 예산 0.25 s 보다 언제나 크다). 지연을
   재고 나서 깎으면 이미 늦다 — 그래서 `compute_load` 의 **예측(모델)** 경로가
   실측 경로와 함께 있어야 하고, 추적기도 감지를 늦추면 안 된다(4번 그림).

5. **다리는 항상 실제로 날 수 있다.** 어떤 감쇄폭에서도 물리 한계 사용이 0.80 을
   안 넘는다(오른쪽 회색). 넘었다면 그건 다리가 아니라 종이 위의 궤적이다.

## 주의

- 위치 경로 실측표는 **1 kg 만** 쟀다. 0 kg 은 질량이 작아 지연에 더 민감할 수도,
  관성이 작아 회복이 빠를 수도 있다 — 추정하지 말고 재야 한다.
- 자세 경로 지연은 지금 **구성값**(`QcConfig.latencyAttS`, 기본 3 ms)이지 온라인 추정이
  아니다. 게이트가 걸린 축이라 이 가정이 틀리면 조용히 위험해진다.
- 다리의 스냅 판정은 기준 궤적의 4차 도함수가 연속인 구간에서만 믿을 만하다.
  `path_time` 출력은 스냅이 뱅뱅이라 이음매 근처에서 과대평가된다 (보수적 방향).
